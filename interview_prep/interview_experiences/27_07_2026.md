## 1. AWS Glue

### Core Concepts

- **AWS Glue** is a serverless data integration (ETL) service. You don't manage servers — Glue provisions Spark environments behind the scenes.
- **Data Catalog**: a persistent, central metadata repository (Hive Metastore compatible). Stores table definitions, schemas, partitions. Shared across Glue, Athena, EMR, Redshift Spectrum.
- **Crawlers**: scan data stores (S3, JDBC, DynamoDB) to infer schema and populate/update the Data Catalog. Can run on a schedule.
- **Glue Jobs**: the actual ETL scripts. Types:
  - **Spark job** (Python/Scala) — most common, runs on managed Spark.
  - **Python Shell job** — lightweight, no Spark, good for small scripts/API calls.
  - **Ray job** — for Python-native distributed processing.
- **DynamicFrame vs DataFrame**:
  - `DynamicFrame` is Glue's own abstraction over Spark DataFrame — handles schema flexibility/semi-structured data (nested JSON, missing fields) better.
  - Convert with `.toDF()` (DynamicFrame → DataFrame) and `DynamicFrame.fromDF()` (back).
  - Use DataFrame when you need full Spark SQL/ML library support; DynamicFrame for schema evolution and `ResolveChoice`, `Relationalize` transforms.
- **Job Bookmarks**: track which data has already been processed so re-runs only process new/changed data (incremental ETL). Stored per job.
- **Triggers**: schedule-based, on-demand, or event-based (job completion chaining) job execution.
- **Workflows**: orchestrate multiple crawlers/jobs/triggers as a DAG.
- **Glue Studio**: visual drag-and-drop ETL authoring tool.
- **Connections**: store JDBC/network config to connect to RDS, Redshift, on-prem DBs (via VPC).
- **Classifiers**: determine the schema/format of data during crawling (built-in for CSV, JSON, Parquet, etc., or custom via grok patterns).
- **Glue Data Quality**: rule-based data quality checks (DQDL - Data Quality Definition Language).

### Common Interview Questions

- **Q: Difference between Glue and EMR?**
  A: Glue is serverless, fully managed, best for standard ETL with less operational overhead but less low-level control and higher per-job cold-start latency. EMR gives full cluster control, supports more frameworks (Hive, Presto, HBase), better for long-running/complex big-data workloads and custom tuning.
- **Q: How does Glue achieve schema-on-read flexibility?**
  A: Via DynamicFrames, which can represent a column as multiple types (`choice` type) and resolve inconsistent schemas with `ResolveChoice`.
- **Q: How do you handle incremental loads?**
  A: Job bookmarks, or manually track a watermark column (e.g., `last_updated`) and use predicate pushdown filters.
- **Q: How do you optimize a slow Glue job?**
  A: Increase DPUs/workers, use G.1X/G.2X worker types appropriately, partition source/target data, avoid `.collect()`, push down predicates when reading, use columnar formats (Parquet), enable job bookmarks to avoid reprocessing, tune `spark.sql.shuffle.partitions`.
- **Q: What is `ResolveChoice`?**
  A: A DynamicFrame transform to resolve ambiguous/conflicting column types (e.g., `cast`, `make_struct`, `make_cols`, `project`).

### Best Practices

- Partition S3 output data (e.g., by date) to improve query performance downstream.
- Use Parquet/ORC over CSV/JSON for performance and cost.
- Avoid excessive crawler runs on large datasets — schedule wisely or use `updateBehavior` settings to control catalog updates.
- Use Glue Data Catalog as a single source of truth accessible by Athena/Redshift Spectrum/EMR — avoid duplicating metadata systems.
- Right-size workers (Standard, G.1X, G.2X, G.025X) based on job memory/CPU needs.

### Sample Snippet

```python
import sys
from awsglue.transforms import *
from awsglue.utils import getResolvedOptions
from pyspark.context import SparkContext
from awsglue.context import GlueContext
from awsglue.job import Job

args = getResolvedOptions(sys.argv, ['JOB_NAME'])
sc = SparkContext()
glueContext = GlueContext(sc)
spark = glueContext.spark_session
job = Job(glueContext)
job.init(args['JOB_NAME'], args)

dyf = glueContext.create_dynamic_frame.from_catalog(
    database="sales_db", table_name="raw_orders"
)

df = dyf.toDF().filter("order_status = 'COMPLETED'")

dyf_clean = DynamicFrame.fromDF(df, glueContext, "dyf_clean")

glueContext.write_dynamic_frame.from_options(
    frame=dyf_clean,
    connection_type="s3",
    connection_options={"path": "s3://my-bucket/curated/orders/", "partitionKeys": ["order_date"]},
    format="parquet"
)

job.commit()
```

## 2. Amazon EMR

### Core Concepts

- **EMR (Elastic MapReduce)**: managed cluster platform for big-data frameworks — Spark, Hadoop, Hive, Presto/Trino, HBase, Flink.
- **Cluster node types**:
  - **Master node**: manages cluster, tracks task status, runs YARN ResourceManager, HDFS NameNode.
  - **Core nodes**: run HDFS DataNode + YARN NodeManager; store data (HDFS) and run tasks.
  - **Task nodes**: only run tasks (compute), no HDFS storage — ideal for Spot instances since losing them doesn't lose data.
- **Storage options**:
  - **HDFS**: local to cluster, fast but ephemeral (lost when cluster terminates unless using EBS-backed persistent clusters).
  - **EMRFS**: EMR's connector letting Spark/Hadoop read/write directly to **S3** as if it were HDFS — enables decoupled, persistent storage (recommended for most modern pipelines).
- **Cluster types**: Transient (spin up, run job, terminate — cost-efficient) vs Long-running (persistent, for interactive/ad-hoc workloads).
- **Instance purchasing**: On-Demand, Reserved, **Spot** (cheap but can be reclaimed — best for task nodes/fault-tolerant stages).
- **YARN**: resource manager that allocates cluster resources (memory/cores) across applications/containers.
- **EMR Notebooks / Studio**: Jupyter-based interactive interface backed by EMR clusters.
- **Auto Scaling / Managed Scaling**: dynamically adds/removes core & task nodes based on YARN memory/pending container metrics.
- **Bootstrap actions**: scripts run on all nodes at cluster launch (install libraries, configure environment).

### Common Interview Questions

- **Q: Why use S3 instead of HDFS with EMR?**
  A: Decouples storage from compute (can terminate cluster without losing data), cheaper, durable (11 nines), scalable, and multiple clusters/services can share the same data. Trade-off: slightly higher latency than local HDFS for very I/O-heavy jobs, and eventual consistency nuances (largely resolved now with S3 strong consistency).
- **Q: How do you reduce EMR cost?**
  A: Use transient clusters, Spot instances for task nodes, S3 over EBS-backed HDFS, right-size instance types, enable Managed Scaling, use Graviton (ARM) instances where supported.
- **Q: What happens if a core node is lost vs a task node?**
  A: Losing a core node can cause HDFS data loss (if replication factor not met) and requires re-computation; losing a task node only affects in-flight compute — no data loss since task nodes don't hold HDFS blocks.
- **Q: EMR vs Glue vs Redshift Spectrum vs Athena — when to use what?**
  A: EMR = full control over cluster/frameworks, heavy custom big-data workloads. Glue = serverless ETL, event-driven pipelines. Athena = ad-hoc serverless SQL queries on S3 data. Redshift Spectrum = query S3 data joined with Redshift warehouse tables.
- **Q: How does speculative execution help?**
  A: Re-launches slow-running ("straggler") tasks on other nodes in parallel; whichever finishes first is used — mitigates skew/hardware slowness.

### Best Practices

- Use S3 + EMRFS for persistent data; treat clusters as transient/disposable compute.
- Separate core (storage+compute) and task (compute-only, Spot-friendly) node groups.
- Tune `spark.executor.memory`, `spark.executor.cores`, and `spark.dynamicAllocation.enabled` for workload.
- Use EMR Managed Scaling instead of manual custom Auto Scaling policies where possible.
- Enable encryption at rest (S3, EBS) and in transit (TLS) for compliance.

## 3. SQL

### Core Concepts

- **Joins**: INNER, LEFT/RIGHT OUTER, FULL OUTER, CROSS, SELF join. Know how NULLs behave in each.
- **Window functions**: `ROW_NUMBER()`, `RANK()`, `DENSE_RANK()`, `LEAD()`/`LAG()`, `NTILE()`, aggregate window functions (`SUM() OVER (PARTITION BY ... ORDER BY ...)`).
- **CTE vs Subquery**: CTEs (`WITH x AS (...)`) improve readability and allow recursion (`WITH RECURSIVE`); subqueries can sometimes be optimized differently by the engine. Neither is inherently faster — depends on optimizer.
- **GROUP BY vs PARTITION BY**: GROUP BY collapses rows into aggregates; PARTITION BY (window function) keeps all rows but computes aggregate per partition.
- **Indexing**: B-Tree (range queries, equality), Bitmap (low-cardinality columns, common in warehouses), Hash (equality only), covering indexes (index includes all queried columns → avoids table lookup).
- **Normalization vs Denormalization**: 1NF/2NF/3NF reduce redundancy (OLTP); denormalization (star/snowflake schema) improves read performance for analytics (OLAP).
- **ACID properties**: Atomicity, Consistency, Isolation, Durability.
- **Isolation levels**: Read Uncommitted, Read Committed, Repeatable Read, Serializable — trade-off between concurrency and consistency.
- **Query execution order** (logical): `FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT`.

### Common Interview Questions

- **Q: Find the 2nd highest salary.**
  ```sql
  SELECT MAX(salary) FROM employees WHERE salary < (SELECT MAX(salary) FROM employees);
  -- or
  SELECT salary FROM (
    SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk FROM employees
  ) t WHERE rnk = 2;
  ```
- **Q: Remove duplicate rows keeping the latest record.**
  ```sql
  DELETE FROM t USING (
    SELECT id, ROW_NUMBER() OVER (PARTITION BY dedup_key ORDER BY updated_at DESC) rn
    FROM t
  ) sub
  WHERE t.id = sub.id AND sub.rn > 1;
  ```
- **Q: Difference between `WHERE` and `HAVING`?**
  A: `WHERE` filters rows before aggregation; `HAVING` filters groups after aggregation.
- **Q: How would you find running totals?**
  ```sql
  SELECT order_date, amount,
         SUM(amount) OVER (ORDER BY order_date) AS running_total
  FROM orders;
  ```
- **Q: How do you optimize a slow query?**
  A: Check the execution plan (`EXPLAIN`), add proper indexes, avoid `SELECT *`, avoid functions on indexed columns in `WHERE`, reduce joins/subqueries where possible, partition/cluster large tables, update table statistics.
- **Q: Explain a self-join use case.**
  A: Finding employees and their managers in the same table:
  ```sql
  SELECT e.name AS employee, m.name AS manager
  FROM employees e LEFT JOIN employees m ON e.manager_id = m.id;
  ```

### Best Practices

- Always check the query plan before assuming a fix will help.
- Filter early (predicate pushdown) — reduce data volume before joining/aggregating.
- Be explicit about join types; avoid implicit cross joins from comma-separated `FROM` lists.
- Use appropriate data types (don't store dates/numbers as strings).

## 4. Python

### Core Concepts

- **Data structures**: list (mutable, ordered), tuple (immutable, ordered), set (unordered, unique), dict (key-value, ordered since 3.7). Know Big-O for lookups/inserts.
- **Mutable vs immutable**: lists/dicts/sets mutable; strings/tuples/ints/frozensets immutable.
- **Comprehensions**: list/dict/set/generator comprehensions — concise and generally faster than manual loops.
- **Generators**: `yield` keyword, lazy evaluation, memory-efficient for large/streaming data. Good talking point for large dataset processing.
- **Decorators**: functions that wrap other functions to add behavior (`@staticmethod`, `@property`, or custom logging/timing decorators).
- **`*args` / `**kwargs`\*\*: variable positional/keyword arguments.
- **GIL (Global Interpreter Lock)**: only one thread executes Python bytecode at a time — CPU-bound tasks don't benefit from threading (use multiprocessing instead); I/O-bound tasks can still benefit from threading/asyncio.
- **Multiprocessing vs Multithreading vs Asyncio**: multiprocessing = true parallelism (separate processes, bypasses GIL) for CPU-bound work; threading = concurrency for I/O-bound work; asyncio = single-threaded cooperative concurrency, great for high-volume I/O (API calls, DB queries).
- **Exception handling**: `try/except/else/finally`, custom exceptions via subclassing `Exception`.
- **OOP**: classes, inheritance, encapsulation, polymorphism, `__init__`, `__str__`/`__repr__`, magic/dunder methods, class vs instance vs static methods.
- **Context managers**: `with` statement, `__enter__`/`__exit__`, useful for resource management (files, DB connections).

### Common Interview Questions

- **Q: Difference between a list and a tuple, and when to use which?**
  A: Lists are mutable and used for collections that change; tuples are immutable, slightly faster, hashable (usable as dict keys), good for fixed records.
- **Q: How do you handle large files that don't fit in memory?**
  A: Use generators/iterators, chunked reading (`pandas.read_csv(chunksize=...)`), or streaming frameworks (PySpark) instead of loading fully into memory.
- **Q: Explain shallow copy vs deep copy.**
  A: Shallow copy (`copy.copy()`) copies the outer object but nested objects are still references; deep copy (`copy.deepcopy()`) recursively copies everything.
- **Q: Write a function to check if a string is a palindrome.**
  ```python
  def is_palindrome(s: str) -> bool:
      s = s.lower().replace(" ", "")
      return s == s[::-1]
  ```
- **Q: How would you deduplicate a list while preserving order?**
  ```python
  def dedup(lst):
      seen = set()
      result = []
      for item in lst:
          if item not in seen:
              seen.add(item)
              result.append(item)
      return result
  ```
- **Q: What are decorators used for in production code?**
  A: Logging, timing/profiling, caching (`functools.lru_cache`), retries, authentication/authorization checks, validating inputs.

### Best Practices

- Prefer built-in functions/libraries (`collections`, `itertools`, `functools`) over manual implementations.
- Write type hints for readability and tooling support (`def f(x: int) -> str:`).
- Use virtual environments (`venv`, `conda`) and pin dependencies (`requirements.txt`, `poetry.lock`).
- Handle exceptions specifically (avoid bare `except:`).
- Use logging module instead of `print()` in production code.

## 5. PySpark

### Core Concepts

- **RDD vs DataFrame vs Dataset**: RDD = low-level distributed collection, no schema, more control but less optimization. DataFrame = distributed collection with schema, benefits from Catalyst optimizer & Tungsten execution engine. Dataset = typed (Scala/Java only, not in PySpark).
- **Transformations vs Actions**: Transformations (`select`, `filter`, `withColumn`, `groupBy`) are **lazy** — build a logical plan (DAG). Actions (`collect`, `count`, `show`, `write`) **trigger execution**.
- **Lazy evaluation**: Spark builds a DAG of transformations and only executes when an action is called — allows the Catalyst optimizer to optimize the whole plan.
- **Catalyst Optimizer**: query optimizer that converts logical plan → optimized logical plan → physical plan (choosing best join strategy, predicate pushdown, etc.).
- **Partitioning**: data split across the cluster. Too few partitions = underutilized cluster; too many = overhead. Rule of thumb: 2–4 partitions per CPU core.
- **Shuffling**: redistributing data across partitions (triggered by `groupBy`, `join`, `distinct`, `repartition`) — expensive (network + disk I/O). Minimize shuffles where possible.
- **`repartition()` vs `coalesce()`**: `repartition()` can increase/decrease partitions and involves a full shuffle; `coalesce()` only decreases partitions and avoids a full shuffle (merges partitions on the same node) — cheaper for reducing partition count before writing output.
- **Broadcast joins**: when one table is small enough to fit in memory, Spark broadcasts it to all executors to avoid shuffling the large table. Triggered automatically below `spark.sql.autoBroadcastJoinThreshold`, or manually via `broadcast(df)`.
- **Caching/Persistence**: `df.cache()` / `df.persist(StorageLevel.MEMORY_AND_DISK)` — store intermediate results in memory to avoid recomputation across multiple actions. Use when a DataFrame is reused multiple times.
- **UDFs (User Defined Functions)**: custom Python functions applied to columns — slower than built-in Spark SQL functions because of Python↔JVM serialization overhead (esp. row-by-row UDFs). Prefer Pandas UDFs (vectorized, Arrow-based) when custom logic is unavoidable.
- **Skew**: uneven data distribution across partitions causing some tasks to take much longer — mitigate via salting keys, broadcast joins, or `skewJoin` optimization (AQE).
- **Adaptive Query Execution (AQE)**: Spark 3.x feature that re-optimizes query plans at runtime based on actual data statistics (handles skew, coalesces shuffle partitions dynamically).

### Common Interview Questions

- **Q: Why are DataFrames generally faster than RDDs?**
  A: DataFrames go through the Catalyst optimizer and Tungsten's efficient memory management/code generation; RDDs are opaque to the optimizer (just JVM/Python objects).
- **Q: How do you handle data skew in a join?**
  A: Salt the skewed key (add a random suffix to spread the data), use broadcast join if one side is small, enable AQE skew join optimization, or pre-aggregate before joining.
- **Q: `repartition` vs `coalesce` — which would you use before writing output files?**
  A: `coalesce()` — avoids a full shuffle since we're just reducing partition count, cheaper.
  ```python
  df.coalesce(10).write.parquet("s3://bucket/output/")
  ```
- **Q: How does Spark achieve fault tolerance?**
  A: Through RDD lineage (DAG of transformations) — if a partition is lost, Spark recomputes it from the lineage rather than replicating all data.
- **Q: When would you use `persist()` over `cache()`?**
  A: `cache()` is shorthand for `persist(StorageLevel.MEMORY_ONLY)`. Use `persist()` explicitly when you want a different storage level, e.g., `MEMORY_AND_DISK` for datasets too large for memory alone.
- **Q: Explain the difference between `narrow` and `wide` transformations.**
  A: Narrow transformations (`map`, `filter`) don't require data movement across partitions — each output partition depends on one input partition. Wide transformations (`groupBy`, `join`, `distinct`) require a shuffle since data must be redistributed.

### Sample Code

```python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.window import Window

spark = SparkSession.builder.appName("interview_prep").getOrCreate()

df = spark.read.parquet("s3://bucket/orders/")

# Broadcast join example
small_df = spark.read.parquet("s3://bucket/dim_customers/")
joined = df.join(F.broadcast(small_df), on="customer_id", how="left")

# Window function: rank orders per customer by date
w = Window.partitionBy("customer_id").orderBy(F.col("order_date").desc())
ranked = joined.withColumn("rn", F.row_number().over(w))

latest_orders = ranked.filter(F.col("rn") == 1)

latest_orders.coalesce(20).write.mode("overwrite").parquet("s3://bucket/curated/latest_orders/")
```

### Best Practices

- Avoid `collect()` on large datasets — brings all data to the driver, can cause OOM.
- Prefer built-in functions (`pyspark.sql.functions`) over Python UDFs for performance.
- Cache DataFrames only when reused multiple times; unpersist when done.
- Use `explain(True)` to inspect physical plans when debugging performance.
- Tune `spark.sql.shuffle.partitions` (default 200) based on cluster size and data volume.
- Write output in columnar formats (Parquet/ORC) with sensible partitioning for downstream reads.

## 6. Snowflake

### Core Concepts

- **Architecture**: Snowflake separates three layers:
  1. **Storage layer** — compressed, columnar micro-partitions stored in cloud object storage (S3/Azure Blob/GCS).
  2. **Compute layer (Virtual Warehouses)** — independent MPP compute clusters; multiple warehouses can query the same data without contention.
  3. **Cloud Services layer** — handles authentication, metadata, query parsing/optimization, access control.
- **Virtual Warehouses**: compute clusters (T-shirt sizes: X-Small → 6X-Large). Can be resized, suspended, and auto-resumed. Billed per-second while running (with a minimum).
- **Micro-partitions**: Snowflake automatically divides tables into small (50-500MB uncompressed) immutable, columnar-stored units with metadata (min/max values) used for **pruning**.
- **Clustering keys**: for very large tables, define clustering keys to co-locate related data in micro-partitions, improving pruning efficiency for filtered queries. (Auto-clustering re-organizes data over time.)
- **Time Travel**: query historical data (`AT`/`BEFORE` clauses) up to 90 days (Enterprise+) — used for recovering deleted/updated data.
- **Zero-Copy Cloning**: instantly clone databases/schemas/tables without duplicating storage — clone only diverges (copy-on-write) when modified. Great for dev/test environments.
- **Streams & Tasks**: Streams track row-level changes (CDC) on a table; Tasks schedule SQL statements (often combined with Streams for incremental pipelines).
- **Snowpipe**: continuous, serverless data ingestion (micro-batch loading) triggered by files landing in cloud storage.
- **Semi-structured data**: native support for `VARIANT`, `OBJECT`, `ARRAY` types — query JSON/Avro/Parquet directly with dot/bracket notation.
- **Data Sharing**: securely share live data with other Snowflake accounts without copying it (Secure Data Sharing / Marketplace).
- **Result caching**: identical queries (same SQL, same underlying data) return cached results instantly without using warehouse compute.

### Common Interview Questions

- **Q: How does Snowflake achieve separation of storage and compute, and why does it matter?**
  A: Storage is centralized in cloud object storage; independent virtual warehouses can spin up/down and scale without affecting other users' compute or the underlying data — enables concurrency without resource contention and pay-per-use compute billing.
- **Q: What is a clustering key and when should you use one?**
  A: A clustering key defines the columns used to co-locate similar rows within micro-partitions. Use it on very large tables (multi-TB) with clear, frequently-filtered columns (e.g., `date`) where natural ingestion order doesn't align with query patterns.
- **Q: How would you implement an incremental/CDC pipeline in Snowflake?**
  A: Use a **Stream** on the source table to capture inserts/updates/deletes, then a **Task** (scheduled or chained) to `MERGE` the changes into the target table.

  ```sql
  CREATE OR REPLACE STREAM orders_stream ON TABLE orders;

  CREATE OR REPLACE TASK merge_orders_task
    WAREHOUSE = etl_wh
    SCHEDULE = '5 MINUTE'
  AS
  MERGE INTO orders_curated t
  USING orders_stream s
  ON t.order_id = s.order_id
  WHEN MATCHED AND s.METADATA$ACTION = 'DELETE' THEN DELETE
  WHEN MATCHED THEN UPDATE SET t.status = s.status
  WHEN NOT MATCHED THEN INSERT (order_id, status) VALUES (s.order_id, s.status);
  ```

- **Q: How do you optimize Snowflake costs?**
  A: Auto-suspend warehouses when idle, right-size warehouses (start small, scale up only if needed), use resource monitors/budgets, leverage result caching, avoid `SELECT *` on huge tables, use clustering only when it actually improves pruning (it also costs credits to maintain).
- **Q: Zero-copy cloning — how is it storage-efficient?**
  A: A clone initially shares the same underlying micro-partitions as the source (metadata pointer copy only); new storage is only consumed when either the clone or source diverges (copy-on-write).
- **Q: Snowflake vs Redshift vs BigQuery — key differentiators?**
  A: Snowflake: true separation of storage/compute, multi-cloud, easy scaling, strong semi-structured data support. Redshift: tightly coupled to AWS, node-based clusters (though RA3/Serverless narrows this gap). BigQuery: serverless, fully pay-per-query, native GCP integration.

### Best Practices

- Use auto-suspend/auto-resume on warehouses aggressively to control cost.
- Load data in bulk via `COPY INTO` (batch) or Snowpipe (streaming/micro-batch) rather than row-by-row inserts.
- Use `VARIANT` for flexible semi-structured ingestion but flatten to structured columns for frequently-queried fields (better pruning/performance).
- Monitor via `QUERY_HISTORY`, `WAREHOUSE_METERING_HISTORY` to identify expensive queries.
- Grant access via roles (RBAC) following least-privilege principle.

## 7. RAG & LLMs

### Core Concepts

- **RAG (Retrieval-Augmented Generation)**: combines a retrieval system (search over your own data) with an LLM's generation capability — grounds LLM responses in external, up-to-date, or proprietary data rather than relying solely on the model's trained/parametric knowledge.
- **Why RAG over fine-tuning?**: RAG is cheaper/faster to update (just update the knowledge base, no retraining), reduces hallucination by grounding answers in retrieved facts, and provides source attribution/citations. Fine-tuning is better for teaching style/format/behavior, not for injecting frequently-changing facts.
- **RAG pipeline stages**:
  1. **Ingestion**: load documents (PDF, HTML, DB records).
  2. **Chunking**: split documents into smaller passages (common strategies: fixed-size with overlap, sentence/paragraph-based, semantic chunking, recursive character splitting).
  3. **Embedding**: convert chunks into dense vector representations using an embedding model (e.g., OpenAI embeddings, Cohere, sentence-transformers).
  4. **Vector storage**: store embeddings in a vector database (Pinecone, Weaviate, Milvus, FAISS, pgvector, Snowflake Cortex Search, OpenSearch).
  5. **Retrieval**: given a user query, embed it and perform similarity search (cosine similarity/dot product/Euclidean) to fetch top-k relevant chunks. Often combined with **hybrid search** (dense vector + sparse/keyword BM25) for best recall.
  6. **Re-ranking** (optional): a cross-encoder re-ranks retrieved chunks for relevance before passing to the LLM (improves precision).
  7. **Generation**: retrieved chunks + user query are inserted into a prompt template and sent to the LLM to generate a grounded answer.
- **Chunk size trade-offs**: too small = loses context; too large = dilutes relevance/wastes context window. Typical starting point: 300–800 tokens with ~10-20% overlap.
- **Embeddings**: numeric vector representations capturing semantic meaning; similar meaning → vectors close together in vector space.
- **Vector index types**: Flat (exact, slow at scale), HNSW (graph-based, fast approximate search), IVF (inverted file index, clustering-based).
- **Context window**: max tokens (input + output) an LLM can process at once — limits how much retrieved context can be injected.
- **Prompt engineering basics**: clear instructions, few-shot examples, system prompts, chain-of-thought prompting, output format constraints (e.g., ask for JSON), providing negative examples.
- **Hallucination mitigation**: grounding via RAG, instructing the model to say "I don't know" when context is insufficient, citation requirements, lower temperature for factual tasks, verification/self-consistency checks.
- **Evaluation metrics for RAG**:
  - Retrieval: precision@k, recall@k, MRR (Mean Reciprocal Rank).
  - Generation: faithfulness/groundedness (is the answer supported by retrieved context?), answer relevance, context precision/recall (e.g., via frameworks like **RAGAS**).
- **Fine-tuning vs Prompting vs RAG**: Prompting = fastest, cheapest, no data needed, limited to what's in context. Fine-tuning = teaches new behavior/style/domain adaptation, requires labeled data & compute, static knowledge (doesn't easily "unlearn"). RAG = dynamic knowledge injection, easiest to keep current, adds retrieval latency & infra complexity.
- **Agentic patterns**: LLMs that can call tools/functions, plan multi-step tasks, and use RAG as one of several tools (tool-calling/function-calling APIs).
- **Guardrails**: input/output validation, PII redaction, content filters, jailbreak/prompt-injection detection especially important when RAG content comes from untrusted/external sources.

### Common Interview Questions

- **Q: Walk me through how you'd design a RAG system for [company's document corpus].**
  A: Outline ingestion → chunking strategy → embedding model choice → vector DB choice (considering scale/latency/cost) → retrieval (hybrid search + re-ranking) → prompt construction → generation → evaluation loop (RAGAS/human eval) → monitoring for drift/hallucination.
- **Q: How do you decide chunk size and overlap?**
  A: Depends on document structure and query type; test empirically — measure retrieval precision/recall at different chunk sizes; use overlap to avoid losing context at chunk boundaries; consider semantic chunking (split at natural topic boundaries) over naive fixed-size splitting for better coherence.
- **Q: What's the difference between dense and sparse retrieval, and why combine them (hybrid search)?**
  A: Dense (embedding-based) retrieval captures semantic similarity even without exact keyword match; sparse (BM25/TF-IDF/keyword) retrieval is precise for exact terms, IDs, acronyms, or rare terms embeddings might miss. Hybrid search combines both (often via reciprocal rank fusion) for better overall recall.
- **Q: How would you reduce hallucinations in a RAG-based chatbot?**
  A: Ensure retrieval quality (better chunking/re-ranking), instruct the model explicitly to answer only from provided context and say "I don't know" otherwise, cite sources, lower temperature, add a verification/fact-checking pass, and monitor with faithfulness metrics.
- **Q: How would you evaluate whether your RAG pipeline improved after a change?**
  A: A/B test with a labeled evaluation set (queries + gold answers/gold context), measure retrieval metrics (recall@k) and generation metrics (faithfulness, answer relevance via RAGAS or human review), track latency/cost trade-offs.
- **Q: When would you choose fine-tuning over RAG?**
  A: When you need the model to adopt a specific tone/format/behavior consistently, do a specialized task (e.g., classification/structured extraction) that benefits from labeled examples, or when latency/cost of retrieval per-query isn't acceptable and knowledge is fairly static.
- **Q: How does a vector database differ from a traditional database?**
  A: Vector DBs are optimized for high-dimensional similarity search (approximate nearest neighbor, e.g., HNSW) rather than exact-match/range queries; many now support hybrid metadata filtering alongside vector search.

### Best Practices

- Keep an evaluation dataset (queries + expected/gold answers) to regression-test the pipeline after any change to chunking, embedding model, or prompt.
- Log retrieved chunks alongside generated answers for debugging/traceability.
- Version your embedding model — re-embedding the whole corpus is required if you switch models (embeddings from different models aren't comparable).
- Set a similarity-score threshold to avoid injecting irrelevant context when no good match exists.
- Consider cost/latency trade-offs of re-ranking and larger context windows in production.
