Data Engineering Interview Prep — Glue, EMR, PySpark, Python, SQL, Snowflake & RAG/LLMs

Use this as a working reference — deep dive sections for Glue, EMR, PySpark, and Python (the core focus areas), plus solid coverage of SQL, Snowflake, and RAG/LLMs for the broader interview.

AWS Glue
What it is
Glue is a serverless ETL and data integration service built on Apache Spark (plus a lightweight Python Shell and, in newer versions, Ray). You don't manage clusters — AWS provisions DPUs (Data Processing Units) behind the scenes. One standard DPU ≈ 4 vCPU + 16 GB RAM.

Core components

| Component    | Purpose                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------- |
| Data Catalog | Central Hive-compatible metastore for table schemas, shared across Glue, Athena, EMR, Redshift Spectrum |
| Crawlers     | Scan data sources (S3, JDBC) and auto-infer schema into the Catalog                                     |
| Jobs         | The actual ETL logic — Spark, Spark Streaming, Python Shell, or Ray job types                           |
| Triggers     | Schedule or event-based job orchestration (on-demand, cron, or job-completion)                          |
| Workflows    | Chain multiple crawlers/jobs/triggers into a DAG-like pipeline                                          |
| Glue Studio  | Visual drag-and-drop ETL builder that generates PySpark code                                            |
| Connections  | JDBC/VPC configs to connect to RDS, Redshift, Snowflake, on-prem DBs                                    |
| DataBrew     | No-code data cleaning/profiling tool (separate from Glue Jobs)                                          |

DynamicFrame vs DataFrame — the #1 Glue-specific interview question

A DynamicFrame is Glue's own abstraction on top of Spark's DataFrame. It's self-describing and tolerant of messy/inconsistent schemas (e.g., a column that's sometimes an int, sometimes a string across files) — something a plain Spark DataFrame will choke on.

| Aspect          | DynamicFrame                                      | DataFrame                             |
| --------------- | ------------------------------------------------- | ------------------------------------- |
| Schema          | Flexible, inferred per-record                     | Fixed, strict                         |
| Performance     | Slightly slower (extra abstraction)               | Faster, native Spark                  |
| Transformations | ResolveChoice, ApplyMapping, relationalize, Unbox | Standard Spark SQL functions          |
| Use case        | Messy/semi-structured data, schema drift          | Clean, well-typed data, heavy compute |

Convert between them freely:

``python
df = dynamicframe.toDF()                        # DynamicFrame -> DataFrame
dyf = DynamicFrame.fromDF(df, glueContext, "dyf") # DataFrame -> DynamicFrame
`

Practice answer: "I usually read raw/messy data as a DynamicFrame to leverage resolveChoice, then convert to a DataFrame for heavy transformations (joins, aggregations, window functions) since Spark DataFrame operations are faster and more familiar, then convert back only if I need Glue-specific sinks/bookmarking."

Job bookmarks (incremental processing)

Bookmarks let a Glue job remember which files/records it already processed, so reruns only pick up new data.

`python
job.init(args['JOBNAME'], args)   # loads bookmark state
...
job.commit()                       # persists new bookmark state
`

Gotcha to mention in interviews: bookmarks work on file modification timestamps (for S3) or a monotonically increasing column (for JDBC) — if you overwrite files in place with the same timestamp, bookmarks can miss changes.

Partition pruning / pushdown predicates

Filter at the catalog level before reading data, not after — this avoids scanning unnecessary S3 partitions.

`python
datasource = glueContext.createdynamicframe.fromcatalog(
    database="salesdb",
    tablename="orders",
    pushdownpredicate="year='2026' and month='07'"
)
`

Distinguish this from .filter() after read (which still scans everything first) — a very common interview trap.

Full job template worth memorizing

`python
import sys
from awsglue.transforms import
from awsglue.utils import getResolvedOptions
from pyspark.context import SparkContext
from awsglue.context import GlueContext
from awsglue.job import Job
from awsglue.dynamicframe import DynamicFrame

args = getResolvedOptions(sys.argv, ['JOBNAME', 'sourcepath', 'targetpath'])

sc = SparkContext()
glueContext = GlueContext(sc)
spark = glueContext.sparksession
job = Job(glueContext)
job.init(args['JOBNAME'], args)

Read with pushdown predicate to skip irrelevant partitions
dyf = glueContext.createdynamicframe.fromcatalog(
database="salesdb",
tablename="orders",
pushdownpredicate="year='2026' and month='07'",
transformationctx="dyf"
)

Switch to DataFrame for transformations
df = dyf.toDF()
dfclean = df.dropDuplicates(["orderid"]).filter(df.amount > 0)

Back to DynamicFrame for schema resolution + write
dyfclean = DynamicFrame.fromDF(dfclean, glueContext, "dyfclean")
dyfresolved = dyfclean.resolveChoice(specs=[("amount", "cast:double")])

glueContext.writedynamicframe.fromoptions(
frame=dyfresolved,
connectiontype="s3",
connectionoptions={"path": args['targetpath'], "partitionKeys": ["year", "month"]},
format="parquet",
transformationctx="datasink"
)

job.commit()
`

Versions & performance
• Glue 3.0 → Spark 3.1, Glue 4.0 → Spark 3.3 / Python 3.10 (adds native Iceberg/Hudi/Delta support), Glue 5.0 → Spark 3.5.
• Worker types: G.1X, G.2X, G.4X, G.8X, G.025X (for light workloads) — know that choosing worker type affects both cost and memory per executor.
• Auto-scaling: Glue can scale executors up/down mid-job (enable via --enable-auto-scaling).
• Continuous logging + CloudWatch metrics for debugging shuffle spill, skew, executor OOM — same tuning knobs as raw Spark (see PySpark section).

AWS EMR
Cluster architecture

`mermaid
graph TD
    A[Master Node<br/>YARN ResourceManager<br/>HDFS NameNode] --> B[Core Node 1<br/>HDFS DataNode + NodeManager]
    A --> C[Core Node 2<br/>HDFS DataNode + NodeManager]
    A --> D[Task Node 1<br/>NodeManager only<br/>no storage]
    A --> E[Task Node 2<br/>NodeManager only<br/>no storage - good for Spot]
`

• Master node — runs cluster management (YARN ResourceManager, HDFS NameNode). Single point unless you enable multi-master.
• Core nodes — run HDFS DataNode + YARN NodeManager. They hold data, so avoid Spot here unless you're okay losing HDFS blocks.
• Task nodes — compute-only, no storage. Ideal candidates for Spot instances since losing one doesn't lose data.

Storage: HDFS vs EMRFS

|             | HDFS                               | EMRFS (S3)                                    |
| ----------- | ---------------------------------- | --------------------------------------------- |
| Persistence | Tied to cluster lifetime           | Independent of cluster — survives termination |
| Use case    | Fast local scratch/shuffle storage | Durable input/output storage                  |
| Cost model  | Pay for EBS/instance storage       | Pay for S3 storage (cheaper, elastic)         |

Best practice: use EMRFS (S3) for data at rest, local HDFS/instance store only for shuffle/temp — and prefer transient clusters (auto-terminate after the job) to avoid paying for idle compute.

Instance groups vs instance fleets
• Instance groups: uniform instance type per role (master/core/task).
• Instance fleets: mix multiple instance types/sizes per role — critical for Spot diversification (reduces risk of mass Spot reclamation), AWS picks best available combination.

EMR Serverless

No cluster to manage — you submit a Spark/Hive job and pay per vCPU-second/memory-second used, with pre-warming to reduce cold start. Good talking point: "EMR Serverless sits between Glue and self-managed EMR — more control than Glue, less ops burden than a persistent cluster."

Comparing Glue vs EMR (classic interview question)

| Aspect        | Glue                            | EMR                                                       |
| ------------- | ------------------------------- | --------------------------------------------------------- |
| Management    | Fully serverless                | Managed cluster or serverless                             |
| Frameworks    | Spark, Python Shell, Ray        | Spark, Hive, Presto/Trino, Flink, HBase                   |
| Startup time  | Fast (~1 min cold start)        | Minutes (cluster provisioning) unless serverless          |
| Cost model    | Per DPU-second                  | Per instance-hour (or vCPU/mem-second serverless)         |
| Customization | Limited (managed runtime)       | Full control — custom bootstrap, configs, libraries       |
| Catalog       | Built-in Glue Data Catalog      | Can use Glue Catalog as external Hive metastore           |
| Best fit      | Standard ETL, incremental loads | Heavy/flexible big-data processing, multi-framework needs |

Practical scenarios worth having a ready answer for
• Small file problem: too many tiny files in S3 slow down job startup (metadata listing) and cause task overhead. Fix with coalesce()/repartition() before writing, or run periodic compaction jobs.
• Data skew: one partition/key has disproportionate volume, causing one task to lag. Fix with salting, skewJoin hints, or AQE skew join optimization (Spark 3+).
• OOM / executor lost: usually driver collecting too much data (.collect() misuse), or too few partitions causing large per-task memory. Fix by repartitioning, tuning spark.executor.memory, avoiding wide collects.
• Cost optimization: use Spot for task nodes, S3 over HDFS, managed scaling, right-size instance types, use EMR Serverless/transient clusters for sporadic workloads.

PySpark (deep-dive — this will likely be the biggest chunk of the interview)
Core architecture

`mermaid
graph LR
    A[Driver Program] -->|creates DAG| B[Cluster Manager<br/>YARN/Kubernetes/Standalone]
    B --> C[Executor 1]
    B --> D[Executor 2]
    B --> E[Executor N]
    C -->|tasks| F[Partitions of data]
    D -->|tasks| F
    E -->|tasks| F
`

• Driver: builds the logical plan (DAG), converts to stages/tasks, schedules work.
• Executors: run tasks on partitions, hold cached data, report back to driver.
• DAG → Stages → Tasks: a job is broken into stages at each shuffle boundary; each stage has one task per partition.

RDD vs DataFrame vs Dataset

|              | RDD                                     | DataFrame                      | Dataset                                        |
| ------------ | --------------------------------------- | ------------------------------ | ---------------------------------------------- |
| Type safety  | Compile-time (generic)                  | Runtime only                   | Compile-time (Scala/Java only, not in PySpark) |
| Optimization | None (no Catalyst)                      | Catalyst optimizer + Tungsten  | Catalyst + Tungsten                            |
| API level    | Low-level, functional                   | High-level, SQL-like           | High-level, typed                              |
| When to use  | Fine-grained control, unstructured data | 95% of real-world PySpark work | Not available in Python                        |

Transformations vs actions (lazy evaluation)
• Transformations (map, filter, join, groupBy, select) build up the DAG lazily — nothing runs yet.
• Actions (collect, count, show, write) trigger actual execution.
• Narrow transformations (map, filter) — no shuffle, data stays in the same partition.
• Wide transformations (groupBy, join, distinct, repartition) — trigger a shuffle across the network, and create a new stage.

Interview soundbite: "Lazy evaluation lets Spark build an optimized end-to-end plan via Catalyst before executing anything, instead of running each line eagerly like pandas."

Shuffling, repartition vs coalesce

`python
df.repartition(200)            # full shuffle, can increase or decrease partitions, evenly distributes
df.coalesce(10)                 # no full shuffle, only merges partitions, can only decrease
`

Use coalesce() before writing output to avoid creating too many small files; use repartition() when you need to fix skewed partition sizes or increase parallelism before a shuffle-heavy operation.

Joins

`python
from pyspark.sql.functions import broadcast

Broadcast join - small table fits in memory, avoids shuffle on large table
result = bigdf.join(broadcast(smalldf), "id")

Handling skewed joins with salting
from pyspark.sql.functions import rand, concat, lit

saltedbig = bigdf.withColumn("salt", (rand() 10).cast("int"))
saltedsmall = smalldf.crossJoin(spark.range(10).withColumnRenamed("id", "salt"))
result = saltedbig.join(saltedsmall, ["key", "salt"])
`

Spark 3+ Adaptive Query Execution (AQE) auto-detects skewed partitions and splits them at runtime — mention this as the modern alternative to manual salting:

`python
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
`

Caching / persistence

`python
df.cache()                                   # MEMORYANDDISK by default
df.persist(StorageLevel.MEMORYONLYSER)     # serialized, saves memory, costs CPU
df.unpersist()
`

Rule of thumb to state in interview: cache a DataFrame only when it's reused across multiple actions — caching something used once just wastes memory.

Window functions

`python
from pyspark.sql import Window
from pyspark.sql.functions import rank, rownumber, sum as sum

w = Window.partitionBy("dept").orderBy(F.col("salary").desc())

df.withColumn("rank", rank().over(w)) \
 .withColumn("runningtotal", sum("salary").over(w.rowsBetween(Window.unboundedPreceding, Window.currentRow)))
`

Know the difference: rownumber() (unique, no ties), rank() (ties share rank, gaps after), denserank() (ties share rank, no gaps).

UDFs vs built-ins vs pandas UDF

`python
Regular UDF - slow, row-by-row, serialization overhead via Python
from pyspark.sql.functions import udf
squareudf = udf(lambda x: x x, IntegerType())

Pandas UDF (vectorized) - much faster, operates on Arrow batches
from pyspark.sql.functions import pandasudf
import pandas as pd

@pandasudf("double")
def squarepandas(s: pd.Series) -> pd.Series:
return s s
`

Always prefer built-in Spark SQL functions first (F.col, F.when, etc.) — they run in the JVM with Catalyst optimization. UDFs are a black box to the optimizer and force JVM↔Python serialization, so only use them when no built-in exists.

Performance tuning checklist (great to recite)
Enable AQE (spark.sql.adaptive.enabled=true) — Spark 3+ default in most managed platforms.
Use broadcast() for small-table joins.
Avoid .collect() on large data; use .take() or write to storage instead.
Partition data on disk by frequently filtered columns (predicate pushdown).
Choose Parquet/ORC over CSV/JSON — columnar formats are faster + support pushdown.
Watch for data skew — check Spark UI stage view for one task taking much longer than others.
Right-size spark.sql.shuffle.partitions (default 200 — often too high for small data, too low for big data).
Avoid wide explode() or collectlist() on huge groups — can blow up memory.

Python
Concepts commonly probed in data engineering interviews
• Mutable vs immutable: lists/dicts/sets are mutable; tuples/strings/frozensets are immutable.
• List/dict/set comprehensions — expected to write these fluently, not use verbose loops.
• Generators (yield) — lazy evaluation, memory-efficient for large file/stream processing (directly relevant to data engineering).
• args / kwargs — variable positional/keyword arguments.
• Decorators — functions wrapping functions (e.g., timing, logging, retry logic — often shown as a practical DE example).
• Exception handling — try/except/else/finally, custom exceptions.
• OOP — classes, inheritance, @staticmethod vs @classmethod, dunder methods (init, repr).
• GIL (Global Interpreter Lock) — only one thread executes Python bytecode at a time; hence multiprocessing (separate processes, true parallelism, good for CPU-bound work) vs multithreading (good for I/O-bound work like API calls/file I/O, not CPU-bound).
• Context managers (with open(...) as f) — resource management, enter/exit.

Retry decorator (common practical ask)

`python
import time
import functools

def retry(maxattempts=3, delay=2):
def decorator(func):
@functools.wraps(func)
def wrapper(args, *kwargs):
attempts = 0
while attempts < maxattempts:
try:
return func(args, *kwargs)
except Exception as e:
attempts += 1
if attempts == maxattempts:
raise
time.sleep(delay)
return wrapper
return decorator

@retry(maxattempts=3, delay=1)
def callflakyapi():
...
`

Generator for large file processing (memory-efficient pattern)

`python
def readlargefile(path, chunksize=100000):
    with open(path, "r") as f:
        lines = []
        for line in f:
            lines.append(line)
            if len(lines) == chunksize:
                yield lines
                lines = []
        if lines:
            yield lines
`

Common coding practice problems

`python
Word frequency count
from collections import Counter
def wordcount(text: str) -> dict:
return dict(Counter(text.lower().split()))

Find duplicates in a list
def findduplicates(items: list) -> list:
seen, dupes = set(), set()
for i in items:
if i in seen:
dupes.add(i)
seen.add(i)
return list(dupes)

Flatten a nested list
def flatten(nested: list) -> list:
result = []
for item in nested:
if isinstance(item, list):
result.extend(flatten(item))
else:
result.append(item)
return result

Group records by key (common ETL pattern)
def groupbykey(records: list[dict], key: str) -> dict:
grouped = {}
for r in records:
grouped.setdefault(r[key], []).append(r)
return grouped
`

SQL
Must-know concepts
• Joins: inner, left/right outer, full outer, self join, cross join, anti-join (NOT EXISTS / LEFT JOIN ... WHERE right.id IS NULL).
• Window functions: ROWNUMBER(), RANK(), DENSERANK(), LAG()/LEAD(), running totals with SUM() OVER (...).
• CTEs (WITH) vs subqueries — CTEs improve readability, and recursive CTEs handle hierarchical data.
• Query optimization: indexing (B-tree vs clustered), reading EXPLAIN plans, avoiding SELECT , filtering early, avoiding functions on indexed columns in WHERE.
• Set operations: UNION vs UNION ALL (dedup cost).

Practice queries

`sql
-- Nth highest salary per department
SELECT dept, salary
FROM (
SELECT dept, salary,
DENSERANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk
FROM employees
) t
WHERE rnk = 2;

-- Running total of daily sales
SELECT orderdate, dailysales,
SUM(dailysales) OVER (ORDER BY orderdate) AS runningtotal
FROM dailysalessummary;

-- Find duplicate rows
SELECT customerid, email, COUNT()
FROM customers
GROUP BY customerid, email
HAVING COUNT() > 1;
`

Snowflake
Architecture (three decoupled layers)

| Layer          | Role                                                                                                                        |
| -------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Storage        | Columnar, compressed, stored in cloud object storage (S3/Azure/GCS), organized as immutable micro-partitions                |
| Compute        | Virtual warehouses — independent MPP clusters, scale up (bigger warehouse) or out (multi-cluster) without affecting storage |
| Cloud Services | Query parsing, optimization, metadata, security, transaction management                                                     |

Key features to know cold
• Micro-partitions — automatic, ~50–500MB compressed chunks; Snowflake auto-tracks min/max per column for pruning. Clustering keys let you influence partition organization for very large tables.
• Time Travel — query/restore data as of a past point (up to 90 days on Enterprise) via AT/BEFORE clauses.
• Zero-copy cloning — instantly clone a table/schema/database without duplicating storage (metadata pointer copy).
• Snowpipe — continuous, event-driven micro-batch ingestion (triggered by S3 event notifications).
• Streams & Tasks — Streams track row-level changes (CDC-like); Tasks schedule SQL execution, often chained with Streams for incremental pipelines.
• Cost control: auto-suspend/auto-resume warehouses, right-size warehouse (T-shirt sizes X-Small to 6X-Large), separate warehouses per workload (ETL vs BI) to avoid contention.

Interview soundbite: "Snowflake's separation of storage and compute means I can scale ETL and BI workloads independently — a heavy Glue/EMR load into Snowflake doesn't compete for resources with analysts running dashboards."

RAG (Retrieval-Augmented Generation) & LLMs
RAG pipeline

`mermaid
graph LR
    A[Documents] --> B[Chunking]
    B --> C[Embedding Model]
    C --> D[Vector Store]
    E[User Query] --> F[Embed Query]
    F --> D
    D --> G[Top-K Relevant Chunks]
    G --> H[Augmented Prompt]
    E --> H
    H --> I[LLM]
    I --> J[Answer]
`

Key concepts
• Chunking strategies: fixed-size (simple, can break context), recursive character splitting (respects paragraph/sentence boundaries), semantic chunking (splits by meaning shift, more expensive to compute).
• Embeddings: numeric vector representations of text capturing semantic meaning (e.g., OpenAI text-embedding-3, Cohere, open-source sentence-transformers).
• Vector stores: Pinecone, Chroma, FAISS (in-memory, good for prototyping), OpenSearch, pgvector (Postgres extension), Snowflake's native VECTOR type.
• Retrieval: cosine similarity / dot product search; hybrid search combines dense vector search with sparse keyword search (BM25) for better recall; re-ranking (e.g., cross-encoder) refines top-K results before sending to the LLM.
• Why RAG over fine-tuning: RAG keeps the LLM's weights frozen and injects fresh/private/domain data at query time — cheaper, faster to update, avoids catastrophic forgetting, and gives traceable sources. Fine-tuning is better for teaching a model a new style/format, not new facts.
• LLM basics: tokens (sub-word units, ~4 chars/token in English), context window limits (how much text fits per prompt), temperature (randomness control), prompt engineering (few-shot examples, system prompts), hallucination (model generating unsupported/fabricated content — RAG mitigates this by grounding in retrieved facts, but doesn't eliminate it).
• Evaluation: retrieval quality (precision/recall of relevant chunks), generation quality (faithfulness — does the answer align with retrieved context — and relevance to the query).

Connecting RAG to your data engineering stack (this is what interviewers actually want to hear)

A realistic story: "I'd use PySpark on EMR/Glue to process and chunk large document corpora at scale, generate embeddings via a pandas UDF wrapping an embedding model (or call an embedding API in batches), and load vectors into a store like OpenSearch or Snowflake's VECTOR type — treating the embedding generation step like any other distributed ETL transformation."

`python
Conceptual pandas UDF for batch embedding generation in PySpark
from pyspark.sql.functions import pandasudf
import pandas as pd

@pandasudf("array<float>")
def getembeddings(textseries: pd.Series) -> pd.Series: # batch call to embedding model/API here
return textseries.apply(lambda t: embedmodel.encode(t).tolist())

chunksdf = chunksdf.withColumn("embedding", getembeddings("chunktext"))
`
